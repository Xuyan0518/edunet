### Coverage vocabulary

- **Active:** reached through a registered page's bound action or lifecycle, or an existing React route. A server rejection or broken UI does not make its caller nonexistent.
- **Retained:** source exists but no current bound/navigation call chain establishes an interactive feature. Registered-only pages, unused helpers and unmounted routers are identified explicitly.
- **Backend-only:** a live handler exists, but no mini program or routed React caller was found. Adding its UI is not automatically mini program parity.
- **Prototype demonstrated:** local navigation, tab/language changes, role simulation, or modal mechanics supported by script. This does not demonstrate authentication or business persistence.
- **Prototype partial:** static read layout/form represents part of a feature, without complete behavior.
- **Prototype toast-only:** the purported business action just produces explanatory text or mock success.
- **Prototype missing:** no meaningful representation. A generic button in another view is not coverage.

## 2. Shared contracts and rules used by the feature matrix

These contracts are part of each matrix row that references them. They avoid repeating long request shapes while keeping methods, permissions, response structures and side effects explicit.

### C1 — Session, role and student scope

`miniprogram/utils/api.js:5` joins the configured base (already including `/api`) with page-relative paths, defaults to GET, sends JSON and `Authorization: Bearer <token>`, resolves any 2xx body and attaches `statusCode` on rejection. `miniprogram/app.js:11` reads cached token/user on launch and directly requests GET `/api/profile` on launch/show (`:25`), updating cached user on success. Error handling here does not constitute automatic logout. React uses `src/config/api.ts:2` and `src/utils/auth.ts:1`, not a separate business API.

The token is a custom signed base64 payload plus HMAC signature, **not JWT**; expiry is seven days (`server/utils/auth.ts:27`, `:51`). Authentication rechecks the relevant role-table record and teacher/parent approval (`server/middleware/auth.ts:13`; `server/utils/auth.ts:95`). `requireTeacher` is strictly teacher and excludes admin (`server/middleware/auth.ts:72`). No general teacher-to-assigned-student ownership table/check is present: ordinary teachers have global student access. Reviewer is a scoped teacher token, not a fourth DB role.

| Code | Meaning and verified scope |
|---|---|
| T | Authenticated, approved teacher. Includes reviewer unless separately blocked/scoped. |
| A | Admin. Allowed only where the handler permits admin; not an automatic substitute for T-only handlers. |
| P | Approved parent, legacy `students.parentId` **or** `student_parent_bindings` membership. |
| R | Teacher token with `isReviewer` and `reviewerStudentId`; student handlers enforce the demo student's ID. R can write several demo-student records. It is not read-only. |
| M | `canManageStudentsAndParents`: admin or teacher whose DB WeChat openid is in the existing allowlist. Recomputed by `requireStudentParentManagement`, not trusted from request JSON (`server/utils/managementPermissions.ts:6`; S:367). |

`GET /api/students` returns all students for T/A, the demo student for R, and the union of bindings and legacy parent linkage for P (S:2442). Parent middleware accepts ID from params/body/query and checks both linkage models (`server/middleware/parentStudent.ts:16`, `:38`, `:65`). Reports additionally check visibility. R is explicitly denied roster changes, parent directory, catalog changes, assignments/sync and cross-student reminders; student English configuration, progress, feedback, exams, papers, reports, AI and bin actions are scoped rather than universally prohibited. Global plan/cycle/term scope gaps are findings in §6, not a proposed permission model.

`POST /api/auth/wechat` takes `{code, role, nickname?, avatarUrl?}` (T/P/A roles); the server uses mini program `jscode2session`, resolves openid then unionid, and may update name/avatar/openid. Existing approved users receive `{token,user}`. First-time T/P without nickname receive `nickname_required`; with nickname they become pending and receive no full session. Existing unapproved accounts return 401 `pending_approval` (including rejected accounts). Admin must already exist, otherwise `admin_not_authorized` (S:523, S:9412). Public user fields are `id,role,name,displayName,avatarUrl,status,authProvider,wechatOpenIdMasked,canManageStudentsAndParents,createdAt,updatedAt` (`server/auth/userIdentity.ts:17`).

`POST /api/auth/reviewer-login` and compatibility alias `/auth/reviewer-login` take `{username,password}`; missing configured demo student or unusable configuration produces 503; invalid credentials fail; success returns a scoped teacher token/user and can create/update the reviewer teacher record (S:9582). No Google, website-WeChat exchange, identity-link or server logout endpoints exist. Existing `/api/login` and `/api/admin/login` still support records with stored passwords; signup, password change and email verification instead return 410. Do not conflate these.

### C2 — Roster, bindings and account administration

Student core data is `id,name,grade,parentId,createdAt` (`server/schema.ts:391`); ordinary list/detail attach `parentIds` and a primary `parentId` (S:787, S:2442). They do not attach parent DTOs; those come from the parent relation endpoint or admin aggregate. Reviewer list returns bare student rows. Student writes accept `{name,grade,parentId?,parentIds?}` and legacy `parent_id`; name length 2–100, grade at most 20 (`server/schema.ts:62`). UI requires a grade. POST requires T/A and excludes R **but lacks M middleware**; PUT/DELETE require M and exclude R (S:2562, S:2606, S:2644). Creation also assigns the ENGLISH subject if found. Parent IDs are deduplicated and bindings plus legacy primary parent are synchronized; full update may replace the entire binding set, so omitting secondary parents is unsafe. Student-add then separately PUTs subject assignments (`M:student-add/index.js:280`).

Binding GET/POST `/api/students/:id/parents` and DELETE `/api/students/:id/parents/:parentId` require T/A+M. POST takes `{parentId}` and returns the refreshed relation data; it checks parent existence, not approval. UI offers approved parents. `/api/parents` lists approved parents for T/A, excludes R, and lacks M; `/parents/unassigned`, `/parents/:id`, `/parents/:id/students`, PUT/DELETE require M. Unassigned means absent from both linkage models. Parent DELETE refuses linked accounts; parent PUT supports name/displayName, avatar and valid pending/approved/rejected status (S:2312–2411).

Admin pending returns `{parents,teachers}` public DTO arrays. `/admin/users` returns identity groups plus role lists; grouping uses unionid, then openid, then role+ID (S:6702). Approval/rejection POSTs take `{id,role}` and update status without a notification. `/admin/users/set-roles` takes `{sourceRole,sourceId,roles[],displayName?}`; roles must be nonempty and valid, display name 1–40 if submitted, source needs WeChat identity. It upserts/deletes records across the three role tables, approves retained T/P, clears stored passwords, and prevents removing the last admin or the calling admin's own role (S:7031). Parent-role removal checks only the legacy parent field; binding-table omission is a defect. `/assign-role` is a separate additive, backend-only operation (S:6952). There is no generic role-change audit history or transactional all-or-nothing guarantee.

### C3 — Catalog, assignment and chapter progress

Public GET `/api/subjects?includeInactive=true` optionally includes inactive rows; default active list. GET `/subject-levels`, `/subjects/hierarchy`, and student `/subjects/full` build default-level-aware output; some read paths call default-level creation/backfill, so GET is not necessarily DB-read-only (S:4787, S:4822, S:5714; `server/utils/subjectLevels.ts:1`). Hierarchy returns `{levels,defaultLevelId}`; student assignment GET returns subject ID array; full returns subject wrappers and recursive topics with status/condition booleans and available timestamps.

Level POST/PUT: `{name,description?,sortOrder?,isDefault?,isActive?}` subject to handler normalization, name 1–64, description up to 240 and sort 0–9999. Default level cannot be disabled/deleted; occupied level cannot be deleted; duplicate name 409. Subject POST/PUT uses `{code,name,level?,levelId?,chineseName?,englishName?,sortOrder?,isRequired?,isActive?}`; code is trimmed/uppercase (≤64), names have schema bounds, default level resolved; inactive matching code can be reactivated, active duplicate conflicts. Subject DELETE forbids required/ENGLISH subjects but **hard-deletes topics, progress, assignments and associated student papers**, including papers in bin. It does not merely hide a subject (S:5087–5359; `server/schema.ts:274`).

Topic POST/PUT: `{code,title,parentTopicId?,orderIndex?,subjectId?}`; code ≤64, title ≤256, order is a string ≤32. Subject+code unique. DELETE refuses children and started progress, removes untouched progress then topic (S:5361–5558). Catalog writes use the global 90-second lock and explicitly reject R.

Assignment PUT `{subjectIds,resetProgress?}` always inserts ENGLISH into the deduplicated set; ENGLISH catalog absence is 500. `resetProgress` is **`removed` (default), `all`, or `keep`**. Default wipes progress for removed subjects, all wipes all student topic progress, keep retains it. It replaces junction rows, not the student or daily history (S:5576). UI auto-selects required subjects, but server only force-includes ENGLISH. Sync POST upserts global topics for selected subject codes from `subjectCatalogs.json`, returning synced/skipped codes and count; it does not reset student progress (`server/utils/catalogSync.ts:63`, `:92`; S:5676).

Progress PUT `/students/:studentId/topics/:topicId/progress` is **T only**, R scoped. Takes either/both condition booleans or valid status. Two true → completed; one → in_progress; neither → not_started. Legacy status-only completed sets both, in_progress sets definition only, not_started clears both. Completing a parent recursively completes all descendants; undoing parent completion does **not** undo descendants (S:5845–5982). Student topic lock is separate from general student-write lock. No client `updatedAt` is required or compared. Although schema has `definitionRecitedAt` and `chapterExerciseCompletedAt` (`server/schema.ts:648`), this handler writes only `updatedAt`, not those two timestamps.

### C4 — Dates, validation, versions and locks

Use date-only `YYYY-MM-DD` wire values and preserve business dates independently of browser timezone. China-date helpers use Asia/Shanghai (`miniprogram/utils/chinaDate.js:1`; `server/utils/chinaDate.ts:1`); some older handlers/UI use local `Date`/date-fns formatting, so not all paths are uniformly timezone-independent. Shared bounds are years 2000–2100; weekly range ≤10 inclusive days, semester/quarterly ≤220, yearly generation ≤380, export ≤370 (`server/utils/inputValidation.ts:8`). Limits are per endpoint: do not apply the 380-day AI allowance to manual report POST's 370-day check or to all analytics routes indiscriminately.

Daily progress, weekly feedback, exams, individual papers and existing legacy summaries require original `updatedAt` on update; their normal deletion endpoints take it in query or body. A mismatch gives 409 `{error:'CONFLICT',updatedAt,updatedByName}`. Missing token gives 400 except legacy-summary handling, which can return conflict for an existing row. Preserve local edits and offer reload; do not silently retry a stale destructive action. Structured reports, bindings, English config and plans do **not** share this optimistic-version contract.

`withActionLock` uses `action_locks`, a unique lock key, expiry and finally-release, returning 409 `{error:'ACTION_LOCKED',message,lock:{lockKey,actionType,actorName,expiresAt,remainingMs}}` (`server/services/actionLocks.ts:73`, `:88`, `:163`). General student writes use 60 seconds, catalog writes 90 seconds; AI takes AI and student-write locks with 240-second TTL (S:229; S:8744; S:8960). This is request-duration exclusion, not an editing lease or revision history. It is not a database transaction, and several handlers read the existing row before acquiring the lock. Review queue, bin operations and several plan/account actions bypass these locks.

Parent scope permits these reads; no parent-sensitive field projection is applied. GET `/progress` returns all active rows (R's demo rows when scoped); **student/date query filters are ignored** (S:7392).

Attendance is present/late/absent; times HH:mm/null; valid date; 1–40 activities; summary ≤5000; usual activity narrative ≤1000 and short text ≤120. Mini publishing additionally requires both times and at least one activity even for absent attendance (`M:daily-progress/detail.js:1864`). Do not infer an absent-day exemption or English-cycle alignment from labels. Normal POST returns 201 normalized row; PUT returns normalized row. Active student+date unique; POST has duplicate conflict check and DB partial index (`server/schema.ts:436`). Normal DELETE soft-deletes only the daily row; it does not delete papers for the day.

### C11 — Bin and irreversible deletion

Soft deletion writes `deletedAt,deletedBy,deletedByName,updatedAt,updatedByName`; active queries exclude deleted rows (S:397). Normal daily, weekly, exams, individual papers, both legacy summaries and structured reports use it. Bin GET `/students/:studentId/bin` T/A, R scoped, returns `{studentId,retentionDays:30,groups}`. Five groups: dailyProgress, weeklyReports, studentReports, exams, papers. **Seven recordType values:** dailyProgress, weeklyReport, studentReport, quarterlySummary, yearlySummary, exam, paper. The studentReports group combines all three report tables (S:2680; `M:student-bin/index.js:3`). Each item includes ID/type/title/summary/original date/deleter/deletion date/daysRemaining.

List filters deletion timestamp to the last 30 days and strict age <30; combined report sublists are concatenated, not one globally sorted cross-type list. Restore POST and permanent DELETE take JSON `{recordType,recordId}` (aliases accepted), require ownership and deleted state, but do **not** enforce retention age or client version and do not lock (S:2845, S:2864). Restore clears deletion fields and refreshes modification metadata, keeps review/status/visibility, sends no notification; a visible report can reappear immediately. Active unique-key collisions may fail restoration. Permanent exam deletion removes scores then exam; other types delete the main row. No undo.

Admin POST `/admin/bin/cleanup-expired` deletes records strictly older than cutoff, returns `{retentionDays,cutoff,results:{type:{count,error?}},failures[]}`; seven types and exam scores, independent failure collection. No scheduled caller or bound mini cleanup action was found (S:2883, S:2923). Thirty days is list visibility/cleanup eligibility, not proof of automatic erasure. Student DELETE `/students/:id` is a separate M-gated **hard deletion** and has no restore. Its missing dependencies/nontransactional behavior are §6 findings, not behavior to deliberately reproduce.

## 8. Dependency-ordered implementation sequence and unresolved decisions

This is a proposed future sequence based on verified gaps; no implementation is authorized or performed by this document.

2. **Establish browser sessions and shared transport.** Decide account-continuity bridge and existing password-user handling; implement profile refresh, scope-aware routing, errors, dates and binary download support. Reuse business `/api` routes. Verify role/approval and identity continuity before dependent screens.

Add four-type review, user approvals/multi-role editor, student admin drilldowns and wellbeing export. Verify exact notification triggers and visibility combinations.
7. **Recovery and browser journeys.** Complete all seven bin types, local previews/copy/download/share and unread markers; then exercise end-to-end journeys with isolated APIs/fixtures and mocked external sends. Include two concurrent clients, deleted/legacy records, denied scope, empty/invalid data, direct URL reload and mobile browser forms.
